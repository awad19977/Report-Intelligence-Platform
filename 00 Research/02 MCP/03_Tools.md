
### **1. What is an MCP Tool?**
An **MCP Tool** is a server-exposed, **model-controlled** primitive that enables an AI model to take actions or execute functions in an external data environment. 

* **Decoupled Control**: Unlike **Resources** (which are read-only "nouns" attached automatically by host application heuristics), **Tools** are the **verbs** of the protocol. They are designed to let the model decide *when* and *how* to invoke them based on its contextual understanding.
* **Stateful Side Effects**: Tools represent dynamic execution paths. They can perform computations, read/write state (such as file modifications or database writes), or invoke remote REST APIs.

---

### **2. Tool Discovery & Capabilities**
To advertise tool capabilities, the server declares the `tools` capability during the **initialization handshake**. The client then discovers available tools using the `tools/list` method.

#### **Capability Declaration (Handshake)**
During protocol initialization, the server declares its capabilities. If it supports tools, it MUST declare the `tools` capability:
* **`listChanged`** (Optional, Boolean): If `true`, the server is capable of sending out-of-band notifications when its tool registry is modified. When the list of available tools changes, the server should emit a `notifications/tools/list_changed` notification to clients, prompting them to re-call `tools/list`.

#### **Tool Discovery (`tools/list`)**
The client fetches the server's tool catalog using the `tools/list` request. This request supports cursor-based pagination and caching.
* **Deterministic Ordering**: The server SHOULD return tools in a deterministic order. This enables efficient prompt caching on the client side and improves LLM prompt cache hit rates when tools are included in the model's context window.

---

### **3. Tool Schemas & Input Parameters**
Every tool is uniquely identified by a name and contains metadata describing its schema.

#### **Tool Definition Object Properties**
* **`name`** (String, Required): The unique identifier.
  * *Constraints*: Must be 1 to 128 characters. Case-sensitive. Allowed characters: ASCII letters (`A-Z`, `a-z`), digits (`0-9`), underscore (`_`), hyphen (`-`), and dot (`.`). No spaces or special characters are allowed.
  * *Disambiguation*: Scope is local to a single server. Clients aggregating multiple servers SHOULD implement a name-spacing strategy (e.g., prefixing with a server identifier) to avoid naming collisions.
* **`title`** (String, Optional): A human-readable display name for the tool.
* **`description`** (String, Optional): An instruction manual for the LLM. High-quality descriptions should front-load verbs and clearly state under what conditions the tool should or should not be utilized.
* **`icons`** (Array, Optional): An array of icons for display in user interfaces.
* **`inputSchema`** (Object, Required): A valid JSON Schema object (defaults to Draft 2020-12 if `$schema` is omitted) defining the expected parameters.
  * *No parameters*: For tools with no parameters, use either `{ "type": "object", "additionalProperties": false }` (recommended) or `{ "type": "object" }`.

#### **Parameter Mirroring (`x-mcp-header`)**
When using the **Streamable HTTP Transport**, servers can designate specific tool parameters to be mirrored into HTTP headers. This allows network intermediaries (proxies, load balancers, WAFs) to inspect and route requests without parsing the JSON body.
* *Syntax*: Placed directly within the property's JSON Schema definition.
* *Header Name*: Becomes `Mcp-Param-{value}`.
* *Constraints*: Must match HTTP field-name token syntax (RFC 9110), must be case-insensitively unique within the schema, and must only be applied to primitive types (`string`, `integer`, `boolean`)—`number` is not permitted. Sensitive parameters (passwords, API keys) must never be marked with `x-mcp-header`.

---

### **4. Output Formats**
Tools return results in either unstructured content arrays, structured content fields, or both.

#### **Unstructured Content (`content` array)**
The `content` field contains an array of content blocks. This enables returning multiple types of media in a single execution:
* **Text Content**: Simple text blocks.
* **Image Content**: Base64-encoded image data with a `mimeType` and optional annotations (audience, priority).
* **Audio Content**: Base64-encoded audio data with a `mimeType`.
* **Resource Links**: A URI to a dynamic resource generated by the tool. This provides a URI that the client can subscribe to or fetch.
* **Embedded Resources**: Complete read-only resources returned directly in the context.

#### **Structured Content (`structuredContent`)**
To return machine-readable results, servers use the `structuredContent` property.
* **Output Schema**: Tools may provide an `outputSchema` in their definition. If defined, the `structuredContent` returned MUST conform to it, and the client SHOULD validate against it.
* **Backwards Compatibility**: Tools that return `structuredContent` SHOULD also return the serialized JSON string in a standard text content block.

---

### **5. Tool Execution Lifecycle & Error Handling**

#### **Execution Lifecycle**
To invoke a tool, the client sends a `tools/call` request containing the tool's `name` and the `arguments` constructed by the LLM. The server executes the operation and returns a JSON-RPC response.

#### **Multi-Round-Trip Requests (`input_required`)**
If a tool requires additional user input during runtime (e.g., OAuth flow, form filling, or a clarifying question), the server can respond with `resultType: "input_required"`. 
This initiates an elicitation sequence. The client gathers the required inputs and retries the `tools/call` by providing `inputResponses` and a correlation `requestState`. The retry MUST use a different JSON-RPC `id` than the initial request.

#### **Dual-Error Reporting Architecture**
MCP employs a dual-error reporting architecture to handle failures gracefully:
1. **Protocol Errors**: Represent fatal bugs in the request structure itself (e.g., unknown tool, malformed requests, or internal server errors). These are returned as standard **JSON-RPC 2.0 error codes** (such as `-32602` for Invalid Params/Unknown Tool) and are unrecoverable for the model.
2. **Tool Execution Errors**: Represent operational or business logic failures (e.g., input validation failures, API timeouts, or business rule violations). These are reported as successful JSON-RPC payloads but with `isError: true` and an explanatory content block. **This allows the AI model to read the failure details and self-correct on the next turn**.

---

### **6. Permissions, Validation, & Safety**
Because MCP Tools authorize arbitrary code execution paths, security boundaries must be strictly enforced:
* **Human in the Loop**: Host applications SHOULD always prompt users for explicit confirmation before invoking any tool. Clear visual indicators must make it clear which tools are being exposed and when tool calls are actively running.
* **Untrusted Metadata**: Tool descriptions and annotations returned from remote servers must be treated as untrusted and sanitized to prevent prompt injection.
* **Input/Output Validation**: Both client and server MUST strictly validate parameters against `inputSchema` and output structures against `outputSchema`. Clients using the Streamable HTTP transport MUST reject and exclude any tool definitions with invalid `x-mcp-header` values.
* **Directory Traversal**: File-writing or reading tools must sanitize path variables to prevent Directory Traversal Attacks (`../`).

### **7. Primitives Comparison Matrix**

The table below contrasts MCP's server primitives with traditional integration methodologies:

| Feature | MCP Resources | MCP Tools | Traditional APIs | Function Calling (Model-Specific) |
| :--- | :--- | :--- | :--- | :--- |
| **Control Model** | **Application-driven** (orchestrated by host heuristics) | **Model-driven** (LLM chooses to invoke via planning) | Impersonated via custom backend code | Hardcoded into specific model provider APIs |
| **State** | Stateless / Read-only data | Stateful / Executable actions with side effects | Arbitrary endpoints | Static schemas sent with each prompt |
| **Real-time Sync** | Highly reactive via subscriptions (`resources/subscribe`) | Transactional; request-response model | Webhook routing / polling | Unmanaged; manual reconciliation |
| **Scaling Complexity** | $N + M$ standard adapters | $N + M$ standard adapters | $N \times M$ fragmented integrations | Proprietary translations per provider |

### **8. JSON Payload Examples**

#### **Example 1: Tool List Request & Response (`tools/list`)**

**Request:**
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list"
}
```

**Response (with explicit Input/Output Schemas and `x-mcp-header`):**
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [
      {
        "name": "execute_sql",
        "title": "Google Cloud Spanner SQL Executor",
        "description": "Execute SQL queries on Google Cloud Spanner. Use this to retrieve or update database records.",
        "inputSchema": {
          "type": "object",
          "properties": {
            "region": {
              "type": "string",
              "description": "The region to execute the query in",
              "x-mcp-header": "Region"
            },
            "query": {
              "type": "string",
              "description": "The SQL query to execute"
            }
          },
          "required": ["region", "query"]
        },
        "outputSchema": {
          "type": "object",
          "properties": {
            "status": { "type": "string" },
            "rows_affected": { "type": "integer" }
          },
          "required": ["status"]
        }
      }
    ],
    "resultType": "complete"
  }
}
```

#### **Example 2: Call Tool Request & Successful Response (`tools/call`)**

**Request:**
```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "execute_sql",
    "arguments": {
      "region": "us-west1",
      "query": "UPDATE users SET status = 'active' WHERE id = 42"
    }
  }
}
```

**Response (Structured and Unstructured Fallback):**
```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "resultType": "complete",
    "content": [
      {
        "type": "text",
        "text": "{\"status\": \"success\", \"rows_affected\": 1}"
      }
    ],
    "structuredContent": {
      "status": "success",
      "rows_affected": 1
    },
    "isError": false
  }
}
```

#### **Example 3: Tool Execution Error (Validation Failure)**
*This is returned as a successful JSON-RPC payload so the LLM can read the feedback and self-correct.*

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "resultType": "complete",
    "content": [
      {
        "type": "text",
        "text": "Invalid departure date: must be in the future. Current date is 08/08/2025."
      }
    ],
    "isError": true
  }
}
```

#### **Example 4: Protocol Error (Invocation of Unknown Tool)**
*This is returned as a fatal standard JSON-RPC 2.0 error code because it is a request structure failure.*

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "error": {
    "code": -32602,
    "message": "Unknown tool: invalid_tool_name"
  }
}
```

#### **Example 5: Multi-Round-Trip Elicitation Request (`input_required`)**

**Initial Response requesting input:**
```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "resultType": "input_required",
    "inputRequests": {
      "github_login": {
        "method": "elicitation/create",
        "params": {
          "mode": "form",
          "message": "Please provide your GitHub username to authorize access",
          "requestedSchema": {
            "type": "object",
            "properties": {
              "name": { "type": "string" }
            },
            "required": ["name"]
          }
        }
      }
    },
    "requestState": "eyJsb2NhdGlvbiI6Ik5ldyBZb3JrIn0..."
  }
}
```

**Retry with Input Response (using a new JSON-RPC ID):**
```json
{
  "jsonrpc": "2.0",
  "id": 4,
  "method": "tools/call",
  "params": {

    "arguments": {

      "query": "SELECT * FROM repositories"
    },
    "inputResponses": {
      "github_login": {
        "action": "accept",
        "content": {
          "name": "octocat"
        }
      }
    },
    "requestState": "eyJsb2NhdGlvbiI6Ik5ldyBZb3JrIn0..."
  }
}
```
